# Scribe Engine v1.3 Release Plan

## Release Theme: "Universal Python Integration"

**Goal:** Make all Python code defined in project files automatically accessible in passages and templates, eliminating the gap between Python definitions and game usage.

---

## Primary Feature: Enhanced Executor System

### Problem Statement
Currently, only classes are made available in the execution context, forcing users to work around limitations when accessing module-level variables like data dictionaries, configuration objects, and utility functions.

**Current Limitations:**
- Module-level variables (e.g., `TOOLS = {...}`) are not accessible in passages/templates
- Users must convert data to functions or classes as workarounds
- Inconsistent behavior: classes work automatically, data doesn't
- Breaks the "natural Python syntax" philosophy

### Solution: Universal Module Loading

**Enhanced `load_systems()` Behavior:**
- **Module Variables** → Directly accessible (e.g., `TOOLS`, `ENEMIES_DB`, `CONFIG`)
- **Classes** → Available for instantiation + Player class auto-instantiated
- **Functions** → Available for calling
- **Maintains backward compatibility** with existing projects

### Implementation Details

**1. Expanded System Loading (`engine/executor.py`)**
```python
def load_systems(self, python_files: List[str]):
    """Load functions, classes, AND module-level variables from .py files."""
    temp_globals = {}

    for py_file in python_files:
        with open(py_file, 'r', encoding='utf-8') as f:
            exec(f.read(), temp_globals)

    # Extract functions, classes, AND non-private variables
    for name, value in temp_globals.items():
        if not name.startswith('__'):  # Skip private/magic attributes
            if isinstance(value, (FunctionType, type)):
                self.systems[name] = value
            elif not callable(value) and not inspect.ismodule(value):
                # Include non-callable, non-module objects (dicts, lists, etc.)
                self.systems[name] = value
```

**2. Template Context Integration (`engine/core.py`)**
- No changes needed - `get_template_context()` already includes `self.executor.get_systems()`
- Module variables will automatically be available in Jinja2 templates

**3. Enhanced Documentation**
- Update user guide with examples of accessible object types
- Document best practices for organizing game data
- Clarify initialization vs. instantiation concepts

### User Experience Improvements

**Before (Current):**
```python
# game_data.py
TOOLS = {"scanner": "Network scanner"}

# Workaround needed
def get_tools():
    return TOOLS
```

**After (v1.3):**
```python
# game_data.py
TOOLS = {"scanner": "Network scanner"}

# Usage in passages - just works!
# {{ TOOLS.scanner }}
```

**Database Patterns:**
```python
# enemies.py
ENEMY_STATS = {
    "goblin": {"health": 30, "damage": 5},
    "dragon": {"health": 200, "damage": 25}
}

class Enemy:
    def __init__(self, enemy_type):
        stats = ENEMY_STATS[enemy_type]
        self.health = stats["health"]
        self.damage = stats["damage"]

# In passages:
# Access data: {{ ENEMY_STATS.goblin.health }}
# Create instance: {$ enemy = Enemy("goblin") $}
```

### Benefits

**Developers:**
- Eliminate workarounds and boilerplate
- Natural Python code organization
- Consistent behavior across all object types

**Engine Architecture:**
- Cleaner separation between data and logic
- No performance impact (no unnecessary instantiation)
- Maintains existing Player class auto-instantiation
